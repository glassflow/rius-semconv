## Notes

**[1] `rius.aggregated_usage.<key>`:** Where a whole agent run's token usage goes when the same producer also
reports each model call's usage on that call's own span:
gen_ai.usage.&lt;suffix&gt; becomes rius.aggregated_usage.&lt;suffix&gt;, on the
in-process (INTERNAL) invoke_agent span only. Left under gen_ai.usage.\*,
the run's tokens are counted once per call span and once more on the
agent span by any backend that sums usage across spans.

Applied only to producers KNOWN to repeat the usage on per-call spans,
because a span on its own cannot say whether its usage is an aggregate
or the only record. CLIENT invoke_agent spans keep their usage: a remote
agent's model calls are not in the trace.

The same move covers a wrapper span that repeats ONE call's usage: a
LiteLLM completion span whose child, the openai instrumentor's
ChatCompletion span, records the call. The child keeps gen_ai.usage.\*,
since it is the call itself. Decided from end order (a child ends
before its parent), so a LiteLLM span with no such child keeps its usage.

Our namespace, not pydantic-ai's gen_ai.aggregated_usage.\*: the GenAI
conventions define no aggregate yet (semantic-conventions-genai#19), and
one could be defined later with different semantics (sub-agents included
or not). A backend reads both spellings, for display only; totals read
gen_ai.usage.\* alone.

**[2] `rius.command.class`:** Classified on the user's machine from the command line, which is never
sent: test, build, lint, package, git, or other. Lets a trace show what a
running or failed shell call was doing without exporting the command.
Claude Code's own telemetry has a similar bash_command_class; no
convention defines the fact.

**[3] `rius.compaction.context_window`:** The limit the context was measured against, so tokens.before reads as how
full the window was. Shared form of what Cursor's preCompact hook reports
as cursor.context.context_window_size.

**[4] `rius.compaction.executor`:** client when the application or agent did the work (it summarized the
history itself, or cut it before sending), provider when the model
provider did it on its side (context editing, a server-side compaction
call). It tells a reader whose behaviour to look at when context
shrinks: the agent's own policy, or a provider setting. Required where
rius.compaction.kind is, for the same reason.

**[5] `rius.compaction.id`:** Lets a reader join a compaction to the record the provider or the agent
keeps for it. Set only when one exists: an id is never made up, as with
gen_ai.conversation.id.

**[6] `rius.compaction.kind`:** How the context was shrunk: summarize (a summary replaces older turns),
clear_tool_results (old tool results are emptied), clear_thinking (old
thinking blocks are dropped) or truncate (old turns are cut with nothing
in their place). A reader needs it because the four lose different
things, and a drop in context between two calls means something else
after each.
Required on a compaction span and a rius.compaction event, which is why
it is conditionally required rather than required: only those carry it,
and a CHAIN or LLM span that is no compaction has nothing to say here.
The span form is keyed by gen_ai.operation.name, not by the span name:
the registry's conventions already key spans by the operation, and
taxonomy.yaml maps "compaction" to the CHAIN kind from it, so a reader
that finds compaction spans by operation needs no name parsing.
A Rius key under rius.\*, never gen_ai.\*: no convention defines a
compaction span or event, and the GenAI registry is free to define one
later and mean something else.

**[7] `rius.compaction.messages.compacted`:** The number of messages that were summarized, cut or emptied, whichever
the kind says.

**[8] `rius.compaction.messages.kept`:** The messages the next call still sees unchanged, usually the most recent
turns. The summary, when there is one, is not counted here.

**[9] `rius.compaction.summary`:** What the summary said, for a summarize compaction. Content in the same
sense messages are: a summary restates the conversation, so it is on
CONTENT_ATTRIBUTES and is masked or stripped at export. Never on a
pending snapshot, since it exists only once the compaction ran.

**[10] `rius.compaction.summary.bytes`:** A size, not content, like rius.context.sizes: deliberately absent from
CONTENT_ATTRIBUTES, so it survives masking and capture_content=False and
a reader can see how big the summary was when its text is withheld.

**[11] `rius.compaction.tokens.after`:** The size of the context the compaction left behind, measured the same
way as rius.compaction.tokens.before.

**[12] `rius.compaction.tokens.before`:** The size of the context the compaction started from, in the model's
tokens. Not gen_ai.usage.input_tokens: that bills one request, while this
measures the context window's contents at a point in time.

**[13] `rius.compaction.tokens.dropped`:** What the compaction removed: tokens.before minus tokens.after when both
are known. Its own key because a provider that clears tool results often
reports only how much it cleared and never the two sizes, and a reader
should not have to subtract to answer "how much was lost".

**[14] `rius.compaction.tool_results.cleared`:** Set for a clear_tool_results compaction, where the messages stay but
their tool results are replaced by a placeholder, so
rius.compaction.messages.compacted does not describe the loss.

**[15] `rius.compaction.trigger`:** auto when the producer or provider compacted because the context neared
its limit, manual when a person or the calling code asked for it (a
/compact command, an explicit call). Absent when the producer cannot
tell. It separates a compaction that was a cost of the run from one
somebody chose.

**[16] `rius.context.sizes`:** Per-part byte sizes of a generation's context, as compact JSON with
readable keys: tool_definitions (name, bytes), input_messages and
output_messages (literal role, parts typed text / tool_call /
tool_call_response with bytes and tool name), cache_marker, and a folded
summary of older input.
A media part (blob / uri / file) carries its modality (image, video,
audio or document) and, when known, byte_size, never bytes: the size of
the media itself, not of any content, which a blob does not carry.
A Rius vendor attribute, NOT a convention:
the backend reads it to attribute gen_ai.usage.input_tokens across the
context, and no convention describes context composition. Deliberately
absent from CONTENT_ATTRIBUTES (it is sizes, not content, and must survive
masking and capture_content=False; that is its whole point when the
messages are truncated or stripped) and from PENDING_IDENTITY_ATTRIBUTES
(content is unknown at span start, so a pending snapshot never has it).

**[17] `rius.main_agent.description`:** Deprecated: moved to gen_ai.main_agent.description.

**[18] `rius.main_agent.id`:** Deprecated: moved to gen_ai.main_agent.id.
Took the same stability constraint the conventions put on gen_ai.agent.id:
a transient in-memory or process-local id here would mint a new "agent"
every restart and make the key useless for grouping.

**[19] `rius.main_agent.name`:** Deprecated: moved to gen_ai.main_agent.name.
Named the agent this process is before the conventions had a key for it.

**[20] `rius.main_agent.version`:** The version of the agent DEFINITION (its prompt, tools and policy), which is
deliberately NOT service.version. A service can sit at 2.3.1 while its
agent definition is at 7, and the two move independently; deriving either
from the other produces confidently wrong data on every deployment where
they disagree, which is most of them.

**[21] `rius.parent.foreign`:** On a span: its parent is local to this process, yet rius never received
it, so the trace arrives without that parent. Remote parents are never
flagged.

**[22] `rius.request.<key>`:** Where a request parameter the GenAI registry does NOT define goes. Our own
namespace rather than gen_ai.request.&lt;key&gt;, per OTel's naming guidance: an
existing semantic-convention namespace must not be used as a prefix for
application-specific attributes, because the convention is free to define
that exact key later and mean something else. The GenAI conventions offer
no catch-all of their own, so we own one.

Masking: rius.request.\* follows gen_ai.request.\* exactly. Today neither is
in CONTENT_ATTRIBUTES, so both export in clear. The TIE is the rule, not
the current value: if request parameters ever become maskable, both
namespaces change together, and neither may join the content allowlist
alone.

**[23] `rius.request.tool_choice`:** How the request constrained tool use: a mode string ("auto", "required")
or, for a forced call, the provider's object as compact JSON. The GenAI
conventions define no tool_choice, so it lives in our namespace. Context
attribution reads it to price the tool-use preamble, which is why the
normalizer lifts it out of the OpenInference request bag (content) into
here (not content).

**[24] `rius.sdk.global_provider`:** On the resource: foreign:&lt;module.Class&gt; when another provider already
held the OpenTelemetry global at init(). Absent when rius registered the
global.

**[25] `rius.span.pending`:** Marks the content-free snapshot exported at span START; the backend maps it
to Finished=0 and the real span replaces it at end. This key knowingly bends
the convention-native rule (no vendor namespace): OpenTelemetry has NO
pending-span mechanism to align with (spec #3732/#4646, semconv #2133, all
open, none planned), and the only shipping precedent (Logfire's
logfire.span_type) is equally vendor-namespaced. Spelled glassflow.span.pending
before the vendor keys moved under rius.\*; the backend reads both spellings
for as long as pre-rename SDK versions are in the field.

**[26] `rius.workspace`:** Process-local routing marker for multi-workspace export. Stamped at span
start so pending snapshots route too, and ALWAYS stripped by the routing
exporter before spans leave the process: the destination's API key is what
tells the backend which workspace a span belongs to.

**[27] `rius.compaction`:** A compaction that happens inside one request, with no step of its own:
the provider edits the context as part of the call, or the agent's hook
reports it while the call is open. It is an event on that LLM span and
carries the rius.compaction.\* attributes. A compaction that is a step of
its own is a CHAIN span with gen_ai.operation.name "compaction" instead,
never both for the same compaction. The first LLM call after either sets
gen_ai.conversation.compacted.
